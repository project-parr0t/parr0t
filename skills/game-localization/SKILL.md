# Parr0t game localization

Read the repository `AGENTS.md`, `docs/agent-usage.md`, and the target workspace `AGENTS.md` before acting. Use the Parr0t CLI as the execution boundary instead of manually translating strings.

Control-plane scope guard: proactively activate the bundled `request-scope-guard` whenever the user limits scope, requests inspection or diagnosis without implementation, changes or narrows an earlier instruction, or when a contemplated action would add optional work, mutate an unrequested target, delete data, commit/push, publish, deploy, install, launch, or otherwise create an external side effect. Prefer the environment's discovered `$request-scope-guard`; when it is unavailable, read the sibling `../request-scope-guard/SKILL.md` and enforce it directly. Re-evaluate the authorization boundary after each user message. The control plane classifies actions and gives workers only the exact authorized targets and side effects; workers must not expand scope independently.

1. Confirm Codex can read the SDK repository and source game folder and can write a separate agent workspace. Prefer sibling folders under one Codex project root. Never use the SDK repository as the data workspace.
2. If there is no workspace, run `game-l10n init-workspace <workspace> --sdk-root <repo> --game-root <game-folder>`. If Git choice is pending, ask the user at the start and record it with `game-l10n policy`; do not infer consent.
3. Run `game-l10n status --workspace <workspace>` and follow its next action. Before touching format tooling, derive the target engine/version compatibility identity from the inspected runtime, run `game-l10n sdk-inventory --refresh-remote` when authenticated network access is available, inspect the public contract and branch-only paths of every plausible `sdk-*` candidate, and bind every `sdk-evaluate` and `sdk-select` call to that target. Reuse or extend only the exact target branch. If a different identity contains useful implementation, record `reference` and select `derive-new`; choose `private-new` only when every candidate is incompatible and none is reusable as a reference. Never turn code reuse into a broader compatibility claim. After selection, inspect the chosen branch's `docs/engine-faq.md` triggers and load a full entry only if its trigger actually occurs.
4. Extract two complete, ordered source inventories with stable IDs and function metadata using independently named methods from the selected SDK; include speakers/scenes when they exist, declare every excluded scope, and run `game-l10n verify-inventory`. Do not start from isolated examples and do not accept one manifest as proof of its own completeness. For partial translation, keep the verified complete primary inventory as `--context-input`. Leave `project.context_mode` at `auto` unless evidence requires `narrative`, `functional`, `knowledge`, or `hybrid` explicitly.
5. Run `game-l10n translate`. It must complete typed context analysis before translation and independent review. Narrative analysis records character/scene evidence; functional analysis records screens, actions, states, conditions, units, and constraints; knowledge analysis records nodes, prerequisites, order, and terminology. Hybrid analysis combines only domains present in the source. Review uses a compact judge, selective rewriter, deterministic validation, and compact confirmation; it rejects material literalism, reference loss, unsuitable tone/rhythm, function changes, condition/unit errors, knowledge-order errors, and material layout risk. The top-level Codex agent monitors status/refusals/fallbacks and deterministic integrity failures; it does not substitute its own semantic review.
6. Treat a provider refusal as a routing event. Let the SDK perform the bounded clarification retry and then use the next configured context, translation, or review provider. Do not obfuscate text or weaken provider safeguards.
7. Pack to a new output path in the agent workspace and validate it without overwriting the installed game. Treat build, fix, test, log inspection, and game-folder access as read-only authorization only. If the user explicitly requests a real install, update, removal, or launch, follow `docs/runtime-approval.md`, record that exact action, and consume the one-shot approval immediately before it. Never infer launch permission from installation permission.
8. Only after the user confirms the patch succeeded, prepare a sanitized engine profile with `promote-sdk` for the exact target identity recorded before implementation, keep it local, and stop. A different-identity reference is only an implementation source and never the promotion destination. Do not propose, ask about, preview, stage, or mention commit, push, repository publication, tags, or releases unless the user first issues an explicit publication command. Only then record approval and use `publish-sdk` to create the target `sdk-<engine>-<version>` from `main`, porting only the verified neutral capability rather than merging a reference SDK branch wholesale.
9. Keep the SDK provenance-free. Do not carry real game/project names, filenames, asset paths, map/event identifiers, dialogue, translations, private exclusions, job metadata, tool paths, hashes, counts, or reports into code, docs, fixtures, commit messages, or history. Use only public engine-format names and unmistakably synthetic fixtures.
10. Follow `docs/engine-faq-contract.md`. Classify each material engine problem as `automated_fix`, `engine_runbook`, `private_only`, or `unresolved`. Deterministic conditions belong in SDK code and regression tests, not documentation. Add or update `docs/engine-faq.md` only when safe continuation requires external tooling, user material, runtime evidence, authorization, or a decision the SDK cannot infer. Keep title-specific incidents private and unresolved causes in the failure queue. An empty reviewed runbook is valid; do not manufacture entries.
11. Treat translation as transformation of one existing target at a time, never generation, continuation, or roleplay. Give each worker the relevant typed context entries, adjacent lines, glossary, immutable constraints, and applicable approved style anchors as context-only evidence; do not resend unrelated context-pack entries. A native worker may receive an exclusive ID shard for scheduling efficiency, but it must load and finalize one target at a time. A refusal must affect only its target ID.
12. Route by configured roles rather than hard-coded provider names. The recommended hybrid uses native Codex translation workers, a separate compact judge, and an independent API for translation fallback, selective rewriting, and judge fallback. API-only, native-only, command, compatible, and local providers may fill each role. Finish the primary translation stage before fallback; return only compact review verdicts; rewrite only flagged targets; confirm corrections; and route only refused/failed judgments to the next judge. Never let the top-level orchestrator substitute its own semantic judgment.
13. Selecting the preset and supplying its key environment variables authorizes its configured automatic calls; do not ask again for every fallback item. If every permitted route or quota is exhausted, preserve the exact source with `source_preserved`. Write only a new patch under the private workspace and never mutate a configured game root.
14. Distinguish API + API from Codex App + API. For the recommended App mode, follow `docs/codex-app-deepseek.md`: use native translator subagents, a separate native compact judge, and the configured external API only for fallback or selective rewriting. Do not treat the signed-in App session as an API key.
15. Keep the top-level agent on the control plane. It may see target IDs, categorical status/error codes, counts, queue transitions, artifact paths, and deterministic issue codes, but must not open dialogue/input/result files or receive source, candidate, translated text, or prose refusal explanations. Have workers read and write private workspace files directly and return metadata-only envelopes.
16. Treat every translation/review refusal as a routing event, not a judgment that the content should be omitted. Normalize its explanation before returning to the parent, continue the staged fallback chain, and still produce the patch with exact source preservation only after all configured routes are exhausted. Use supported low-creativity generation settings; never claim or attempt to disable provider safeguards.
17. Follow `docs/execution-budget.md`. Produce the minimum requested artifact first, cap repeated attempts at the same failure, reuse unchanged validation results, and stop testing when the proportional acceptance checks pass. Do not turn a one-click installer, minor fix, or packaging request into a legacy migration or rollback framework.
18. Keep small, coupled tasks in the current agent. Use subagents for independent bulk translation/review shards only when parallelism materially reduces elapsed time; do not delegate simple packaging, one-file fixes, or redundant QA.
19. For a Steam delivery package, follow `docs/steam-packaging.md`. Feed an already built payload and a private spec to `game-l10n steam-package`. Use the generated receipt-based installer instead of copying job-specific installation logic into the repository. Building or validating the ZIP does not authorize invoking its mutating modes.
20. The public per-game repository workflow is dormant until the user first explicitly commands publication; before that command, never mention, propose, ask about, preview, or prepare a destination repository, commit/push, tag, GitHub Release, release gate, or upload. Once activated, follow `docs/instance-release.md`. Target the player's environment, default to Windows unless another platform is explicitly specified, and derive architecture and prerequisites from the supported game build. Preserve the user's existing README with minimal reviewed changes. Build once from a clean tagged commit, upload the exact verified bytes, record the source/tag/release and file hashes, and make every supported original game version/build agree across the README, release notes, manifest, asset name, and installer binding checks. Use the visible title `<Game Display Name> Patch <Patch Version> (Game Version <Game Version>)`, or the exact enumerated `Game Versions` form.
21. For a Windows distribution, follow `docs/installer-contract.md`. Do not improvise package filenames, core error codes, or player messages, and never place the agent harness or approval artifacts in the release. The player interface has Install, Restore, and Verify installed state; it uses `parr0t-patch-status.txt` as the patch-ID marker. Put deterministic SDK/title failures in the custom `PARR0T-<SCOPE>-E###` registry. Interactive player confirmation is sufficient; only noninteractive agent/script mutation uses runtime approval.
22. For Steam discovery and launch integration, follow `docs/steam-faq.md` and `docs/wrapper-executable.md`. Select a game only from the exact app manifest plus binding checks. Never read or edit `localconfig.vdf`, launch options, or per-account client configuration, and never require or terminate Steam. Use only exact approved, reproducible, signature/hash-verified Parr0t wrapper bytes for the target architecture—not `.lnk` or a per-game build—at each declared main-executable path, and preserve the real original with `replace_files`. Only a separately confirmed action may close the validated target game process.
23. Follow `docs/coverage-gates.md`. Context files require a successful per-part execution attestation; provider capacity or another operational failure must fall back and cannot be treated as completion. A full review of existing work uses `game-l10n review-existing` and judges every target, not just changed or flagged targets. Keep static inventory, result alignment, semantic review, and runtime coverage as separate claims.
24. Preserve capacity, timeout, rate-limit, quota, authentication, malformed-response, and other operational failures in the metadata-only failure queue. Resume with `game-l10n resume-failures` only after a later explicit user request. If an unresolved target is marked `metadata.blocking_on_failure=true`, keep the whole result set in the private held checkpoint and emit no new patch artifact.
25. Follow `docs/release-checkpoint.md`. Every distribution includes a validated `parr0t-release-checkpoint.json`. If the user supplies an earlier release with the game folder, import it before model calls and regenerate the current inventories. A new build requires new release validation but does not invalidate every translation; reuse only exact unchanged reviewed targets whose compatible SDK, source, location, dependency, and target-scoped context/review bindings still match. For a requested wording change, invalidate the named IDs plus their declared reverse dependencies instead of translating everything again. Implement and verify a safe missing-locale fallback only when the selected SDK supports it; otherwise record an explicit unsupported reason.
26. Follow `docs/segment-metadata.md` for composed UI strings. Have the selected SDK emit slot role, semantic state, related IDs, render pattern, fixed target affixes, and hard limits only when backed by format or call-site evidence. Translate and review the slot payload rather than surrounding UI chrome. If an already patched game root appears changed, use the read-only `game-l10n inspect-installed-state` receipt check before broad re-extraction; its `possible_game_update` state is advisory, while damaged preserved-original backups block mutation.
27. For an exact user-specified typo or wording correction, use `docs/minimal-corrections.md` and `game-l10n apply-user-correction`. Keep the work in the current agent, make no model or context calls, preserve every unnamed result, and reuse the existing SDK/package inputs. Repack the owning payload once and verify once. Do not delegate, repeat discovery, inspect the installation, hash the whole game, re-review unchanged targets, or create task-specific correction scripts. Review only explicitly reported reverse dependencies.
28. For native App translation or review, use `prepare-native-pass` v2 and start one fresh worker per task with `fork_turns="none"` or the host's no-history equivalent. Never reuse a completed worker through follow-up tasks. Pass only private artifact paths and the immutable worker contract, keep source/candidate/tool output out of messages, and require a metadata-only final envelope. The defaults are at most 32 IDs and 12,000 estimated private material tokens per task; reduce them for large focused context or output. This worker rotation is required even when cached input is cheap because accumulated conversation history causes superlinear token replay and latency.

Never copy source game data, extracted strings, translations, caches, logs, prompts, or keys into the SDK repository.

## Unity 2021.3 branch

On `sdk-unity-2021.3`, read `docs/unity-2021.3.md` and run `game-l10n unity discover` before selecting a build path. Keep the existing Mono workflow for Mono players. For IL2CPP players, generate interop assemblies offline with a compatible private-workspace BepInEx toolchain, then compile the private bridge with `build-il2cpp`. Treat the player binary, metadata, loader references, and Unity base libraries as read-only inputs; keep generated assemblies and patch packages outside the SDK repository.
