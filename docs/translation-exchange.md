# Translation exchange contract

`parr0t.translation-exchange/v1` is the only supported handoff format for manual translation and translation fallback outside the direct provider pipeline. It exists so the control plane never opens private text files, invents a spreadsheet or JSON shape, or converts a provider failure into a semantic decision.

## Boundary

The bundle stays under the private game workspace. A data-plane worker, authorized API adapter, or human translator may open its text-bearing files. The top-level orchestrator may see only the JSON printed by the CLI, the workspace-relative `control-envelope.json` path, and the validated metadata-only receipt. It must not open `exchange-manifest.json`, `requests.jsonl`, `success.jsonl`, or `failure.jsonl` and must not create an alternative handoff file.

Create a bounded bundle with:

```text
game-l10n prepare-translation-exchange \
  --workspace <workspace> \
  --input <ordered-segments.jsonl> \
  --output <private-exchange-directory> \
  --exchange-id <stable-id> \
  --mode manual|fallback \
  --source-queue primary_pending|translation_fallback_pending
```

Each bundle contains 1–2,000 ordered targets and exactly these files:

```text
exchange-manifest.json
requests.jsonl
success.jsonl
failure.jsonl
exchange-receipt.json       # generated by seal
control-envelope.json       # generated by seal
```

Do not rename, add fields to, or replace these files with CSV, Markdown, a new JSON object, a script-generated report, or chat prose.

## Immutable request rows

`requests.jsonl` is generated once and must not be edited. Every row has exactly:

```json
{
  "target_id": "synthetic-line-001",
  "ordinal": 0,
  "source": "Synthetic source text.",
  "source_sha256": "<lowercase-sha256>",
  "context": {
    "speaker": "Synthetic Speaker",
    "scene": "synthetic-scene",
    "previous": "",
    "next": "",
    "metadata": {}
  },
  "context_sha256": "<lowercase-sha256>"
}
```

The source and relevant context travel together. Sentence-level failure isolation therefore does not remove character voice, scene flow, UI role, glossary-related metadata, or adjacent evidence.

The exchange row is not itself a provider prompt. An authorized data-plane adapter resolves the workspace's typed context, projects only evidence relevant to this target, and calls the configured provider adapter. It must not copy the complete context pack or exchange bundle into `context.metadata`, build a job-local API request loop, or resend completed successes. The configured input preflight and usage telemetry apply to fallback exchange processing as they do to the direct pipeline.

## Success rows

Write a successful candidate to `success.jsonl` with exactly:

```json
{
  "target_id": "synthetic-line-001",
  "status": "success",
  "text": "SYNTHETIC_TARGET_TEXT",
  "route": "manual",
  "attempt": 1,
  "source_sha256": "<copied-from-request>",
  "context_sha256": "<copied-from-request>"
}
```

A success is only a translation candidate. Sealing routes it to `review_pending`; it must never be represented as independently reviewed.

## Failure rows

Write a failed attempt to `failure.jsonl` with exactly:

```json
{
  "target_id": "synthetic-line-002",
  "status": "failed",
  "failure_code": "timeout",
  "route": "fallback-provider",
  "attempt": 1,
  "source_sha256": "<copied-from-request>",
  "context_sha256": "<copied-from-request>",
  "retryable": true
}
```

Allowed failure codes are the fixed route-failure `FailureCode` values; terminal `source_preserved` and review-only user acceptance are excluded. There is deliberately no `reason` field: refusal prose, source excerpts, safety labels, and semantic explanations stay out of the control plane. A missing row remains pending. Neither a failed nor a missing row is an exclusion or success.

## Seal and continue

Run:

```text
game-l10n seal-translation-exchange \
  --workspace <workspace> \
  --bundle <private-exchange-directory>
```

The validator rejects modified requests, unknown or duplicate IDs, overlap between success and failure, extra fields, invalid codes, stale source/context digests, or empty success text. It writes `parr0t.translation-exchange-receipt/v1` and a validated `parr0t.control-envelope.v2`.

- Every success moves to `review_pending`.
- Every explicit failure and missing row remains `translation_fallback_pending` and is reported to the parent only as `fallback_required` (shown to Korean users by the existing control-plane UI as the standard fallback-needed label).
- A partial seal is a resumable checkpoint and exits nonzero; complete additional rows in the same bundle and seal again.
- Never route directly from this bundle to `source_preserved`. That state still requires the separate complete route-evidence contract.
- Manual and fallback modes use the identical row format. Switching provider or handing a remainder to a human does not authorize format conversion, re-extraction, or retranslating valid successes.

The control plane acts only on the sealed envelope. If it reads a text-bearing exchange file or creates another format, record `parent_opened_data_plane` or `unvalidated_worker_response` and rotate the control plane.
