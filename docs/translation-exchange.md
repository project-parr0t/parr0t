# Translation exchange contract

`parr0t.translation-exchange/v1` is the only supported handoff format for manual translation and translation fallback outside the direct provider pipeline. It exists so the control plane never opens private text files, invents a spreadsheet or JSON shape, or converts a provider failure into a semantic decision.

## Boundary

The bundle stays under the private game workspace. A data-plane worker, authorized API adapter, or human translator may open its text-bearing files. The top-level orchestrator may see only the JSON printed by the CLI, the workspace-relative `control-envelope.json` path, and the validated metadata-only receipt. It must not open `exchange-manifest.json`, `requests.jsonl`, `success.jsonl`, or `failure.jsonl` and must not create an alternative handoff file.

Create a bounded bundle with:

```text
game-l10n prepare-translation-exchange \
  --workspace <workspace> \
  --input <ordered-segments.jsonl> \
  --output <private-exchange-directory> \
  --exchange-id <stable-id> \
  --mode manual|fallback \
  --source-queue primary_pending|translation_fallback_pending
```

The `--output` directory path must use only `[A-Za-z0-9._-]` segments, because its receipt path is reported through the control plane.

Each bundle contains 1–2,000 ordered targets by default, or the explicitly configured record limit, and these interchange files:

```text
exchange-manifest.json
requests.jsonl
success.jsonl
failure.jsonl
exchange-receipt.json       # generated by seal
control-envelope.json       # generated by seal
```

Do not rename, add fields to, or replace these interchange files with CSV, Markdown, a new JSON object, a script-generated report, or chat prose. Additional immutable route/attempt receipts are Core-owned lineage, not another worker interchange format.

## Immutable request rows

`requests.jsonl` is generated once and must not be edited. Every row has exactly:

```json
{
  "target_id": "synthetic-line-001",
  "ordinal": 0,
  "source": "Synthetic source text.",
  "source_sha256": "<lowercase-sha256>",
  "context": {
    "speaker": "Synthetic Speaker",
    "scene": "synthetic-scene",
    "previous": "",
    "next": "",
    "metadata": {}
  },
  "context_sha256": "<lowercase-sha256>"
}
```

The source and relevant context travel together. Sentence-level failure isolation therefore does not remove character voice, scene flow, UI role, glossary-related metadata, or adjacent evidence.

JSONL records are separated by LF, not Unicode text separators. Literal NEL (`U+0085`), line separator (`U+2028`), and paragraph separator (`U+2029`) remain part of source, context, and candidate strings through exchange collection, retries, prior-result review, and corrections. Adapter results must match both the bound target ID and exact source; a stale source cannot acquire the current request's digests.

The exchange row is not itself a provider prompt. An authorized data-plane adapter resolves the workspace's typed context, projects only evidence relevant to this target, and calls the configured provider adapter. It must not copy the complete context pack or exchange bundle into `context.metadata`, build a job-local API request loop, or resend completed successes. The configured input preflight and usage telemetry apply to fallback exchange processing as they do to the direct pipeline.

## Success rows

Write a successful candidate to `success.jsonl` with exactly:

```json
{
  "target_id": "synthetic-line-001",
  "status": "success",
  "text": "SYNTHETIC_TARGET_TEXT",
  "route": "manual",
  "attempt": 1,
  "source_sha256": "<copied-from-request>",
  "context_sha256": "<copied-from-request>"
}
```

A success is only a translation candidate. Sealing routes it to `review_pending`; it must never be represented as independently reviewed.

## Failure rows

Write a failed attempt to `failure.jsonl` with exactly:

```json
{
  "target_id": "synthetic-line-002",
  "status": "failed",
  "failure_code": "timeout",
  "route": "fallback-provider",
  "attempt": 1,
  "source_sha256": "<copied-from-request>",
  "context_sha256": "<copied-from-request>",
  "retryable": true
}
```

Allowed failure codes are the fixed route-failure `FailureCode` values; terminal `source_preserved` and review-only user acceptance are excluded. There is deliberately no `reason` field: refusal prose, source excerpts, safety labels, and semantic explanations stay out of the control plane. A missing row remains pending. Neither a failed nor a missing row is an exclusion or success.

## Seal and continue

Run:

```text
game-l10n seal-translation-exchange \
  --workspace <workspace> \
  --bundle <private-exchange-directory>
```

The validator rejects modified requests, unknown or duplicate IDs, overlap between success and failure, extra fields, invalid codes, stale source/context digests, or empty success text. It writes `parr0t.translation-exchange-receipt/v1` and a validated `parr0t.control-envelope.v2`.

- Every success moves to `review_pending`.
- Explicit failures and missing rows remain pending and are reported only as `fallback_required`.
- A partial seal preserves validated successes and unresolved rows. Continue with the still-pending work; an incomplete bundle is not permission to skip targets or block independent work.
- Never route directly from this bundle to `source_preserved`. That state requires actual evidence that applicable configured semantic routes were attempted and exhausted; repair-needed or unattempted targets remain pending.
- Manual and fallback modes use the identical row format. Switching provider or handing a remainder to a human does not authorize format conversion, re-extraction, or retranslating valid successes.

The control plane acts only on the sealed envelope. If it reads a text-bearing exchange file or creates another format, record `parent_opened_data_plane` or `unvalidated_worker_response` and rotate the control plane.

A Core-prepared fallback bundle uses the job's exact approved route graph. Process its next contiguous external-provider block with:

```text
game-l10n process-translation-exchange --workspace <workspace> --bundle <bundle>
```

The command validates unchanged requests and completed rows, executes only that external block, preserves successes and consumed attempt ordinals, writes fixed rows, and seals the bundle. It never skips over a Native successor to reach a later API provider, promotes a fallback to primary, or performs independent review. Existing job authorization permits continuation; a fresh human request is not required. `--retry-failures` still respects route eligibility and never replays an unchanged operational failure.

Failed-only retry checkpoints retain failures not yet attempted. Completed successes replace old failures; interrupted checkpoints remain resumable without overlapping IDs. Preserve failure history and retry only eligible failed targets under the configured policy.

When failed targets next require a Native route, the metadata-only response contains `native_continuation` with a frozen predecessor receipt and failed-only source path. Continue without reading that source:

```text
game-l10n prepare-native-pass \
  --workspace <workspace> \
  --input <native_continuation.source> \
  --output <fresh-private-native-pass-directory> \
  --predecessor-receipt <native_continuation.receipt>
```

Core verifies the receipt, source fingerprint, exact next Native route and target subset. Preserve the predecessor through retries; later external blocks use the same frozen graph. Never rebuild the order by filtering out Native providers or infer whole-chain exhaustion from one completed block. A successful command exit may mean this handoff succeeded, not that translation or the patch is complete; `local_patch_ready` remains authoritative.

When starting retries for that successor pass, forward `--content-source-manifest <prepared-native-manifest>` to `start-native-translation-retries`. This carries the verified predecessor and source authority into the new retry state; provider names in result rows are not authority to reconstruct the route.

Collect the complete mixed-transport job through Core, never by concatenating private review files:

```text
game-l10n collect-native-followup \
  --workspace <workspace> \
  --input <original-ordered-inventory> \
  --collect-chain \
  --followup <root-followup> \
  --successor-followup <successor-followup> \
  --review-output <private-full-review-input.jsonl> \
  --unresolved-output <private-unresolved.jsonl>
```

Repeat `--successor-followup` in route order; `--collect-chain` also supports a single native follow-up preceded by an external block. Core verifies inventory binding, predecessor edges and frozen parent snapshots, preserves earlier successes, and remains partial until every root target is accounted for. Collecting one earlier scope alone can legitimately return incomplete even after successors finish; do not rewrite its sealed failures to simulate completion. Collected candidates still require the configured review.

For direct API jobs, `resume-failures` retains prior attempts and candidates. Status schedules only a provably eligible route attempt or deterministic acceptance step; unchanged exhausted or operationally failed routes and missing lineage produce a metadata repair action rather than an automatic replay loop. Successful targets are never retransmitted.

No whole-job usage limit is required by default. The configured DeepSeek adapter still applies its focused per-request input preflight automatically. Do not ask the user to choose a token, time, call, or cost ceiling before fallback or as a condition of starting the job.

If the user independently requested whole-job ceilings, bind each chosen dimension at the first applicable bundle and provide only the accounting evidence required for those dimensions:

```text
game-l10n process-translation-exchange \
  --workspace <workspace> \
  --bundle <bundle> \
  --max-input-tokens <whole-job-cap>
```

For a selected elapsed-time ceiling, supply `--max-elapsed-minutes <whole-job-cap>` and its bound `--budget-started-at-epoch <original-job-start>` instead. A confirmed prior-usage baseline is needed only when prior metered usage is included in the selected token ceiling. Do not require unrelated dimensions.

The core records provider-reported usage for selected metered dimensions, checkpoints each wave, and preserves the same ceilings on later bundles. Do not require baselines or start times for dimensions without a user-set ceiling. For a selected token ceiling, an unknown prior baseline or interrupted metered event remains explicitly uncertain; reconcile only with exact provider-reported evidence, never task-size estimates or empty counters.

Once selected, a ceiling cannot be silently dropped while work remains. Cached results do not incur historical usage again; known usage is persisted before progress callbacks. Uncertain metered events remain uncertain until exact evidence resolves them. Processing and its usage ledger require a single writer.

When an explicitly requested ceiling is reached, already sealed successes remain cached, untouched targets remain pending in the same exchange, and no further provider call starts. This budget checkpoint is not permission to narrow scope, preserve source early, or open a new format.
