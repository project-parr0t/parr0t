# AGENTS.md — Parr0t repository

Parr0t contains reusable orchestration code only. Never place actual game files, extracted strings, translations, prompts, caches, logs, or credentials here.

## Required agent behavior

1. Create every per-game working directory outside this repository with `game-l10n init-workspace`.
2. At the beginning of a game task, ask whether Git use is allowed and record the choice with `game-l10n policy`. A refusal means no `git init`, branch, commit, or push for that task.
2a. Before writing or adapting unpack, apply, pack, or validation code, run the SDK inventory gate in `docs/sdk-selection.md`. Inspect every plausible local and remote-tracking `sdk-*` branch by its public contract, record compatibility with `game-l10n sdk-evaluate`, and select `reuse`, `extend`, or `private-new` with `game-l10n sdk-select`. Reuse is the default, extension is preferred over duplication, and `private-new` is permitted only after every inventoried candidate is categorically incompatible. Do not use branch-name similarity alone and do not copy an existing adapter into a new implementation.
3. Analyze the complete ordered source inventory before translating. Use `auto`, `narrative`, `functional`, `knowledge`, or `hybrid` context as appropriate; do not force UI-, logic-, or guide-heavy data into a story schema. Do not translate from isolated examples. If all context-analysis routes fail or refuse, stop.
4. The top-level orchestrator monitors completion, refusal, malformed output, integrity checks, and fallback routing. It does not perform semantic review.
5. Use independent translation and review routes. A refusal or invalid result must move to the next configured provider.
6. Keep character voice, formality, forms of address, story/scene state, screen actions and states, conditions, units, knowledge order and prerequisites, glossary terms, placeholders, markup, and control codes consistent. Preserve communicative function, idiomatic target-language phrasing, supported allusions/wordplay, deliberate alterations, and function-appropriate tone/rhythm. Do not approve a mechanically literal result merely because its denotational meaning is correct, and do not invent a reference from weak resemblance.
7. Only after the user explicitly confirms that the translation/patch succeeded may a reusable unpack/pack tool be prepared with `game-l10n promote-sdk`.
8. After successful preparation, keep the sanitized profile local and stop. Do not propose, ask about, preview, stage, or mention commit, push, repository publication, tags, or releases unless the user first gives an explicit publication command. Only then record the matching approval and use `game-l10n publish-sdk`.
9. Engine branches are named `sdk-<engine>-<version>`, branch from `main`, and contain only reusable SDK/tool files.
10. Run `python scripts/check_repo_privacy.py` and `python -m unittest discover -s tests -t . -v` before committing.
11. Translation is a bounded transformation of existing user-provided text, never scene generation, continuation, roleplay, or endorsement. Translate one target segment per provider request while supplying only its relevant typed context: narrative/voice evidence, functional screen/state evidence, knowledge/prerequisite evidence, adjacent lines, glossary rules, and immutable constraints. A native worker startup may receive one exclusive target-ID shard to amortize scheduling, but it must load, translate, and record each target independently rather than treating the shard as one batch prompt. A refusal for one target must never cancel, suppress, or contaminate unrelated targets.
12. When the user selects a provider preset and supplies its API-key environment variables, that selection authorizes automatic calls through the configured context, translation, judge, rewriter, and fallback chains; do not stop for a second per-item fallback approval. Follow configured roles rather than hard-coded vendor identities. Complete each primary translation stage before fallback, use compact review verdicts, rewrite only flagged targets, confirm corrected candidates, and route only refused/failed judge targets to the next judge. Record refusal metadata without text. If every permitted route or quota is exhausted, keep the exact source with status `source_preserved`.
13. Treat every configured game root as immutable. Translation files, rebuilt data, archives, and patches must be new outputs under the external agent workspace. Never overwrite or install into the source game unless the user separately requests installation after reviewing a recoverable patch.
14. Distinguish API providers from native Codex App workers. In the recommended App + DeepSeek mode, use native GPT-6 Luna translator subagents and a separate native GPT-6.1 Sol compact judge; use DeepSeek only for configured translation fallback, selective rewriting, and judge fallback, and require only `DEEPSEEK_API_KEY` for those external calls. The signed-in App session is not an API key. This is a recommended preset, not a core dependency; follow `docs/codex-app-deepseek.md` and keep the top-level agent orchestration-only.
15. Separate the data plane from the orchestration control plane. The top-level agent may receive target IDs, categorical status/error codes, counts, queue transitions, artifact paths, and deterministic issue codes only. It must not open dialogue/input/result files, receive candidate text, or receive a provider's prose refusal explanation. Workers read private files themselves, write results under the private workspace, and return metadata-only completion envelopes.
16. A translation or review refusal is only a routing event, never a content judgment and never grounds for omitting the target or cancelling patch creation. Normalize provider explanations to categorical codes before they reach the parent. DeepSeek requests use the faithful-transformation prompt and deterministic low-creativity settings supported by the API; do not claim or attempt to disable provider safeguards.
17. Treat `main` as the engine-neutral control framework. Engine discovery, unpacking, application, packing, verification, engine-specific FAQ entries, and engine fixtures belong only to the relevant `sdk-<engine>-<version>` branch. Dependencies flow from `main` to SDK branches, never from an SDK branch back into `main`. Follow `docs/sdk-branch-contract.md`.
18. When starting or resuming a localization job, follow `docs/agent-usage.md`. Use `docs/prompt-examples.md` when constructing a user-facing task prompt. Keep the public `README.md` concise; detailed execution procedures belong in agent documentation rather than the public landing page.
19. Deliver the smallest artifact that satisfies the current request before considering optional hardening. Do not invent legacy migration, rollback archives, compatibility layers, exhaustive backups, or generalized installers unless the user requested them or a demonstrated requirement blocks the minimal artifact. Freeze scope at each user request; a translation task does not authorize unrelated installer or SDK redesign.
20. Calibrate verification to the changed layer and stop after the required checks pass. Reuse successful results while their input fingerprint is unchanged. For a packaging-only change, run focused package validation and one synthetic lifecycle; do not repeatedly hash the entire source game, rebuild unchanged translation data, relaunch the game, or rerun broad suites without a new failure or changed input. Follow `docs/execution-budget.md`.
21. Use the current agent for simple fixes, packaging, documentation, status inspection, and other tightly coupled work. Delegate only genuinely independent bulk translation/review shards or parallel research that materially shortens elapsed time. Never create a subagent merely to recheck work that already has a deterministic validator.
22. Steam delivery support on `main` is distribution-layer tooling, not an engine adapter. Build it from an already prepared payload with `game-l10n steam-package`; keep the payload and package spec in the private workspace. The generic installer may discover Steam libraries, fall back to an explicit directory, and manage only receipt-owned files. Do not embed a previous package, build a universal migration system, or inspect engine assets in this layer.
23. Treat a configured game root as read-only authorization only. A request to build, fix, inspect, validate, check logs, or diagnose runtime data does not authorize installing a patch, updating or removing an existing patch, launching the game, executing a generated plugin, or deleting generated runtime data.
24. Real `install`, `update`, `remove`, and `launch` actions require separate explicit user approvals. Record each approval only after the user requests that exact action, bind it to the current artifact digest, exact configured target, exact executable for launch, and a short expiry, then consume it once immediately before the external effect. Never reinterpret install approval as launch approval or create a production approval merely to make an automated test pass; isolated repository tests may use synthetic approval fixtures against temporary roots only.
25. Default to user-executed runtime validation. Automated validation uses synthetic temporary targets only. A new artifact digest, target, executable, action, expired record, or consumed record invalidates approval; do not regenerate it without a new user instruction. Engine SDK adapters that add real installation or launch behavior must call the shared runtime approval guard.
26. A public per-game instance workflow is dormant until the user first explicitly commands publication of that instance. Before that command, do not mention, propose, ask about, preview, or prepare any publication repository, commit/push, tag, GitHub Release, release gate, or upload. After activation, follow `docs/instance-release.md`; target the player's execution environment, default to Windows unless another platform is named, and derive architecture and prerequisites from the supported game build. Build once from a clean tagged commit and upload the exact verified bytes; bind the tag, source commit, release ID, package/manifest/file hashes, and embedded versions as one release unit. Record every supported original game version/build and make the README, release notes, manifest, asset name, and installer checks agree. Preserve the user's existing README with minimal reviewed edits. The visible GitHub Release title must be `<Game Display Name> Patch <Patch Version> (Game Version <Game Version>)`, using `Game Versions` for an explicitly enumerated multi-build release.
27. Every player-facing Windows installer follows `docs/installer-contract.md`. Use the fixed package layout, Korean player messages, core result-code meanings, and the public operations Install, Restore, and Verify installed state. Determine ownership first from `<game-root>/parr0t-patch-status.txt` and its patch ID, then from the matching receipt. A payload that must replace an original file declares its target and backup path before packaging; first install preserves the verified original, update reuses that same backup, and Restore puts it back. Never infer or rotate an original backup during update. SDK/title-specific failures may use only the separate `PARR0T-<SCOPE>-E###` registry and cannot redefine core codes. Never ship or apply the agent harness, approval JSON, prompts, task state, logs, or workspace policy to a distribution. Interactive menu choice plus final confirmation is the player's authorization; only noninteractive agent/script mutation requires runtime approval.
28. For Steam discovery and launch integration, follow `docs/steam-faq.md` and `docs/wrapper-executable.md`. Resolve a game through registry roots, existing libraries, the exact app manifest, and declared binding files; ask when no unique validated root exists. Never read or edit `localconfig.vdf`, Steam launch options, or other per-account client configuration, and never require, close, kill, or restart Steam. Steam Play-button integration uses the exact approved, reproducible, Authenticode-verified Parr0t wrapper bytes for the target architecture at each explicitly declared main-executable path, with the real original governed by `replace_files`; `.lnk` shortcuts and per-game ad hoc binaries are not executable replacements. Require the game to be closed for locked replacements; only a separately confirmed adapter action may close the validated game process inside the selected root.
29. The control plane must proactively use `skills/request-scope-guard/SKILL.md` whenever the user limits or narrows scope, asks for read-only inspection/diagnosis, or a contemplated action is optional, unrequested, destructive, or externally consequential. Prefer a discovered `$request-scope-guard`; otherwise read and apply the bundled file directly. Re-evaluate after every user message, and give subagents or provider workers only the exact authorized targets and side effects. No worker may infer permission to expand scope, clean up data, commit/push, publish, deploy, install, launch, or contact an external system.
30. Require two independently produced, complete ordered source inventories before context analysis or translation. Each selected SDK extractor declares its method and every excluded scope; a user-visible exclusion makes static coverage incomplete. `manifest_missing=0` means only that results align with the verified manifest and must never be reported as zero in-game omissions. Runtime coverage is a separate state and stays `not_run` until metadata from a user-executed or separately authorized observation is recorded.
31. Treat context analysis as complete only when the CLI records successful execution for every part plus the evidence-coverage attestation. Files left by an interrupted worker, capacity failure, provider error, or partial route are not completion evidence. Use the configured fallback route; if every context route fails, stop before translation.
32. Candidate reuse is not semantic re-review. When the user asks for a complete re-review, every current target—including unchanged and previously unflagged entries—must receive a fresh independent verdict under the current context through `game-l10n review-existing`. Never present stable IDs, matching digests, structural validation, or a flagged-subset review as a full semantic review.
33. Put capacity, timeout, rate-limit, quota, authentication, malformed-response, and other operational failures in the metadata-only failure queue. Resume it only after a later explicit user request. SDK extractors mark indispensable targets with `metadata.blocking_on_failure=true`; while any such target is unresolved, hold the complete result set in the private workspace and emit no new patch artifact. Nonblocking exhaustion may preserve exact source but must remain visible as incomplete review/coverage metadata.
34. Every distributable package includes the validated `parr0t-release-checkpoint.json` defined by `docs/release-checkpoint.md`. When a prior release and a game folder are supplied, import that checkpoint before model work and re-extract the current inventories. A new game build invalidates direct installation compatibility, not every translation: reuse a reviewed target only when its source, location, dependency, target-scoped context/review, and compatible SDK-adapter bindings still match. A user-requested correction invalidates only the named IDs and their declared reverse dependencies unless the user requests complete review or the global review policy changed. Missing-locale fallback is best-effort: verify a safe base-locale, source-text, or nonempty-placeholder path when the selected SDK supports one; otherwise record `unsupported` with a neutral reason and never claim the protection exists.
35. Follow `docs/segment-metadata.md` for composed UI text. When static call-site or format evidence is available, SDK extractors identify whether a target is a standalone string, label, value, state value, or template fragment; record its render pattern, related IDs, semantic state, fixed target affixes, and hard character limit when known. Translators and reviewers operate on the slot payload only and never duplicate surrounding UI chrome. Before treating a patched-root mismatch as an upstream game update or re-extracting the whole game, run the read-only `game-l10n inspect-installed-state` receipt check. `possible_game_update` is advisory evidence of a changed receipt-owned file, not proof of its cause; a damaged original backup is a hard stop before mutation.
36. An exact user-specified typo or wording fix uses `docs/minimal-corrections.md` and `game-l10n apply-user-correction`. Keep it in the current agent, bind it to the verified inventory and release checkpoint, reuse the released full results when available, and make zero model calls or context-analysis runs. The checkpoint materializes the released candidates when the full result artifact is unavailable. Do not reopen source discovery, delegate the fix, inspect or hash the complete game tree, re-review unchanged targets, or create job-specific apply/validation scripts. Repack only the owning payload and verify the new package once. If reverse dependencies exist, stop the fast path and review only those IDs; if the target mapping is ambiguous, perform one narrow static lookup.

## Zero-provenance SDK rule

The SDK repository must reveal nothing about any localization job. This applies to the current tree, documentation, tests, fixtures, commit messages, branch descriptions, tags, and retained history.

- Never retain a real game title, developer/publisher, character or location name, dialogue, translation, source filename, asset/resource path, map/event identifier, job-specific tool/workspace path, model/provider used for a job, run count, timestamp, hash, report, or description of what private game data was edited.
- Engine-defined canonical names may appear only when required to implement or document the public file format. Test-only identifiers and text must be unmistakably synthetic (`fixture`, `synthetic`, `SOURCE_*`, `TARGET_*`) and must not be copied from a game.
- Reimplement the minimal reusable behavior from a private workspace; never copy its notes, examples, exclusions, fixtures, logs, or reports. Before publishing, inspect both the final diff and branch history. If provenance entered an unpublished branch, amend/squash it; if it reached a remote branch, rewrite that branch with `--force-with-lease` after explicit authorization.

## Neutral FAQ maintenance

Actively record reusable problems in `docs/faq.md`, but only after removing all provenance. An entry is eligible only when it follows from the SDK/engine design or can reasonably recur across independent projects.

- Use the format: symptom, general cause, diagnosis, resolution, prevention.
- Do not mention where or when the issue occurred, the affected game or files, actual job commands/paths, source or translated text, specific model/provider identities, counts, hashes, screenshots, or outcomes from a particular job.
- Keep project-specific incidents only in the external private workspace. If an issue cannot be useful without private details, do not add it to the repository FAQ.
- Update or merge an existing FAQ entry instead of accumulating job narratives.

API keys belong in environment variables. Do not print or persist them.
